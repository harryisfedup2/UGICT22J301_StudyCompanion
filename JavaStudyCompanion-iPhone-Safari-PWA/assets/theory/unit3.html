Unit 3: Interfaces, Exceptions & Threads

Interfaces describe capabilities, exceptions describe abnormal outcomes, and threads let several tasks make progress within one process. A useful analogy is a busy clinic: an interface is the service promise, an exception is a clearly signaled problem such as an unavailable test, and threads are separate staff members. Shared patient records need rules (synchronization), or two people can overwrite each other's updates.

Defining and implementing interfaces

An interface declares a contract that unrelated classes can implement. A caller can depend on the interface instead of a specific implementation, making programs easier to extend and test. A class uses implements; a class may implement several interfaces. An interface cannot be instantiated directly.

Traditional interface methods without bodies are implicitly public abstract. Interface fields are implicitly public static final constants. Modern Java also supports default and static methods with bodies; private helper methods can be used by interface methods. A functional interface has one abstract method and can be implemented with a lambda, though lambdas are not required for this syllabus example.

interface Notifier {
    void send(String message);
    default void sendReminder() {
        send("Please check your course notice.");
    }
}

class ConsoleNotifier implements Notifier {
    @Override
    public void send(String message) {
        System.out.println("Notice: " + message);
    }
}

class InterfaceDemo {
    public static void main(String[] args) {
        Notifier service = new ConsoleNotifier();
        service.sendReminder();
    }
}

Line by line: Notifier names a capability and declares send. Its default method reuses the contract by calling send. ConsoleNotifier supplies the required public implementation. The variable is typed as the interface, so main is coupled to the promise rather than the concrete class. The default reminder calls the implementation's send method through dynamic dispatch.

Expected output: Notice: Please check your course notice.

An abstract class is a good fit when related classes share state or partial implementation and one superclass relationship makes sense. An interface is a good fit for a capability or contract that different class families can share. A class can extend only one class but implement multiple interfaces.

Exception handling: failures as explicit control flow

An exception is an object that signals an abnormal condition and transfers control to a matching handler. The root family is Throwable, with two major branches: Error for serious problems applications usually should not try to recover from, and Exception for conditions an application may handle. RuntimeException and its subclasses are unchecked; other exception subclasses are checked by the compiler.

Checked exception

The method must catch it or declare it with throws. Examples include many I/O failures. This makes the caller consider a recoverable failure path.

Unchecked exception

A RuntimeException subclass need not be caught or declared. Examples include null dereference, invalid indexing, and invalid numeric parsing. These often indicate invalid input or a programming error.

Error

Represents serious runtime or environment trouble, such as resource exhaustion or linkage problems. Broadly catching Throwable can hide failures and is rarely appropriate.

Place risky operations in a try block. A matching catch handles a compatible exception. A finally block normally runs as control leaves the try/catch, but it can be bypassed by process termination or a catastrophic VM failure; use try-with-resources for closeable resources. Catch specific exceptions before broader ones because a broad catch first would make later specific catches unreachable.

throw raises one exception object. throws declares possible checked exceptions in a method signature. A custom checked exception commonly extends Exception; a custom unchecked exception extends RuntimeException. Preserve the cause when wrapping a lower-level exception so debugging retains context.

class InvalidAgeException extends Exception {
    InvalidAgeException(String message) {
        super(message);
    }
}

class Admission {
    static void verifyAge(int age) throws InvalidAgeException {
        if (age < 18) {
            throw new InvalidAgeException("Applicant must be at least 18");
        }
    }

    public static void main(String[] args) {
        try {
            verifyAge(16);
            System.out.println("Eligible");
        } catch (InvalidAgeException error) {
            System.out.println("Rejected: " + error.getMessage());
        } finally {
            System.out.println("Verification complete");
        }
    }
}

Line by line: InvalidAgeException defines a domain-specific checked failure. Its constructor passes the message to Exception. verifyAge declares the checked exception with throws; the condition constructs and raises it with throw. In main, the call is inside try. If it returns, “Eligible” prints. Here the exception is caught, its message is shown, and the finally block prints the completion message in either path.

Expected output:
Rejected: Applicant must be at least 18
Verification complete

Common exception mistakes

  • Catching Exception too early and losing the chance to handle cases differently.
  • Writing an empty catch block that silently discards important information.
  • Using exceptions for ordinary branching, such as checking every array index instead of using the length.
  • Assuming finally always runs under every possible process-ending event.
  • Throwing a broad generic exception when a meaningful subtype would explain the contract better.
  • Confusing throw (raise an object now) with throws (declare a method's checked failure possibilities).

Java thread model and multithreaded programming

A process is an executing program with its own resources; a thread is an execution path within a process. Threads in the same process can share heap objects, which enables efficient communication but creates risks when multiple threads access mutable state. A CPU may run threads on separate cores or interleave them on one core; the Java specification describes allowed behavior without requiring one scheduling strategy.

Java's Thread object represents a thread. Define work by implementing Runnable (usually the more flexible design) or extending Thread when specializing Thread is truly needed. Call start() once to request a new thread of execution; calling run() directly is an ordinary method call on the current thread. Use join() when one thread must wait for another to finish.

Thread.StateMeaning
NEWCreated but not yet started.
RUNNABLEExecuting in the JVM or eligible to run; Java's state model does not expose a separate RUNNING state.
BLOCKEDWaiting to acquire a monitor lock.
WAITINGWaiting indefinitely for another action, such as notification or completion of a joined thread.
TIMED_WAITINGWaiting for a bounded time, such as during sleep or timed wait.
TERMINATEDExecution has completed.

Thread priorities range from MIN_PRIORITY (1) to MAX_PRIORITY (10), with NORM_PRIORITY (5) as the default. A priority is a scheduling hint, not a guarantee of order or fairness. Correctness must never depend on one thread winning a race because it has a higher priority. sleep pauses the current thread for a time and does not release locks it already holds; interrupt is a cooperative signal that code should respond to, not a forceful thread kill.

Creating a thread with Runnable

class GreetingTask implements Runnable {
    private final String name;
    GreetingTask(String name) { this.name = name; }
    @Override
    public void run() {
        System.out.println("Hello from " + name);
    }
}

class StartThreadDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(new GreetingTask("worker"));
        worker.start();
        worker.join();
        System.out.println("Main continues after worker");
    }
}

The task stores the message data and implements run. A Thread is constructed with that task. start begins a separate execution path. join makes the main thread wait for its completion, so the final line comes afterward. Without coordination, output ordering between threads is not generally predictable.

Synchronization, communication, and deadlocks

A race condition occurs when a result depends on the timing of unsynchronized accesses. For example, count++ is a read, calculation, and write, not one indivisible operation. If threads share a mutable object, guard related state with a shared lock or use a suitable concurrent utility. A synchronized instance method locks that object's monitor; a synchronized static method locks the class's Class object. Keep critical sections short and use the same lock consistently.

class SafeCounter {
    private int value = 0;
    synchronized void increment() { value++; }
    synchronized int getValue() { return value; }
}

class CounterTask implements Runnable {
    private final SafeCounter counter;
    CounterTask(SafeCounter counter) { this.counter = counter; }
    public void run() {
        for (int i = 0; i < 10000; i++) counter.increment();
    }
}

public class Unit3Threads {
    public static void main(String[] args) throws InterruptedException {
        SafeCounter counter = new SafeCounter();
        Thread first = new Thread(new CounterTask(counter));
        Thread second = new Thread(new CounterTask(counter));
        first.start();
        second.start();
        first.join();
        second.join();
        System.out.println(counter.getValue());
    }
}

Line by line: SafeCounter owns mutable state. Both read and write operations use its monitor, so increments cannot interleave in a way that loses an update. Each Runnable holds the same counter reference and performs 10,000 increments. Two Thread objects start the tasks concurrently; join ensures both have completed before the final read. Since the protected operation is atomic with respect to this lock, the result is stable.

Expected output: 20000.

Inter-thread communication with wait and notify

wait, notify, and notifyAll are methods of Object and must be called while holding that object's monitor. A waiting thread releases the monitor and sleeps until notification, interruption, or timeout; it must reacquire the monitor before continuing. Always test a condition in a while loop because notification does not prove the condition is now true, and spurious wakeups are permitted. Prefer higher-level tools such as blocking queues for producer-consumer work in real applications.

synchronized (lock) {
    while (!conditionIsReady()) {
        lock.wait();
    }
    useReadyData();
}
// A producer changes the state under the same lock, then calls lock.notifyAll().

Deadlock

A deadlock is a cycle of threads permanently waiting for locks held by one another. The classic necessary conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait. Prevention strategies include acquiring multiple locks in a global order, minimizing nested locking, using timeouts where suitable, or replacing shared locking with message passing. Java does not generally guarantee detection or automatic recovery from application-level deadlocks.

History, applications, and common errors

Java's original design already treated threads and synchronization as language-and-runtime concerns rather than requiring each program to invent a separate threading model. This supported interactive and networked programs that needed multiple activities to progress. The formal Java Language Specification now describes threads, locks, and the memory model in its own chapter. Modern applications often use executors, futures, and concurrent collections instead of manually creating many raw threads, but the fundamentals in this unit explain how those tools behave.

  • Calling run() instead of start() does not create a new thread.
  • Calling start() twice on the same Thread throws IllegalThreadStateException.
  • Assuming thread output will appear in a fixed order when no synchronization establishes one.
  • Assuming a high priority guarantees earlier execution.
  • Using wait without owning the monitor causes IllegalMonitorStateException.
  • Checking a wait condition with if instead of a loop can make code incorrect after spurious wakeups or competing consumers.
  • Synchronizing on different lock objects does not protect shared state consistently.
  • Swallowing InterruptedException; code should normally restore the interrupt flag or propagate the exception.
  • Holding locks while doing slow I/O increases contention and can contribute to deadlocks.

Interfaces help with plug-in services and test doubles; exceptions support resilient file, network, and input handling; threads support concurrent servers, background tasks, user interfaces, and parallel work. For safety, prefer immutable data and well-tested concurrency utilities when they fit.

Viva practice · 40 answered questions

1. What is an interface?

An interface defines a contract that implementing classes agree to provide. It lets callers depend on a capability rather than one concrete class.

2. Which keyword implements an interface?

A class uses implements, followed by one or more interface names. It must provide required abstract methods unless the class is abstract.

3. Can one class implement multiple interfaces?

Yes. Java allows one class to implement several interfaces, which supports multiple capabilities without multiple class inheritance.

4. What is a default interface method?

It is an interface method with a body declared using default. It can provide shared behavior while remaining overridable by implementing classes.

5. What are interface fields?

They are implicitly public static final, so they are constants associated with the interface rather than per-object state.

6. Interface or abstract class: when to choose?

Use an interface for a capability shared by possibly unrelated classes. Use an abstract class when related subclasses should share instance state or partial implementation.

7. What is an exception?

An exception is a Throwable object that signals an abnormal condition and transfers control toward a matching handler or caller.

8. What is the root of Java's exception hierarchy?

Throwable is the root class. Its two main branches are Error and Exception.

9. What is a checked exception?

It is an exception other than RuntimeException or Error that the compiler requires a method to catch or declare. Many I/O exceptions are checked.

10. What is an unchecked exception?

A RuntimeException or Error subclass is unchecked. The compiler does not require it to be caught or declared.

11. What is the difference between Error and Exception?

Error generally signals serious conditions an application is not expected to recover from; Exception represents conditions a program may handle or report.

12. What does try do?

A try block encloses code whose exceptions will be handled by following catch blocks or whose resources should be managed by try-with-resources.

13. What is catch used for?

A catch block handles a thrown exception whose type is compatible with its parameter. Catch narrow cases before broader types.

14. What is finally?

A finally block is used for cleanup when control leaves a try/catch construct. It is not guaranteed after process termination or severe VM failure.

15. What is try-with-resources?

It automatically closes declared AutoCloseable resources when leaving the block. It is preferred for resources such as streams and database connections.

16. Distinguish throw and throws.

throw raises a specific exception object. throws declares possible checked exceptions in a method signature.

17. How do you create a custom checked exception?

Define a class that extends Exception, usually with a constructor accepting a message and passing it to super(message).

18. Why should catches be ordered from specific to general?

A broad catch can match every subclass case below it, making those later catches unreachable. Specific-first order also documents recovery choices.

19. What is a thread?

A thread is an execution path within a process. Threads in one process share heap objects and other process resources.

20. Process versus thread?

A process has its own address space and resources; a thread is one path of execution inside a process. Threads share memory within their process.

21. How can Java work be defined for a thread?

Implement Runnable and provide its run method, or extend Thread. Runnable separates the task from the thread mechanism.

22. Why call start instead of run?

start asks the JVM to create a separate execution path that later calls run. Calling run directly executes like an ordinary method on the current thread.

23. Can a Thread object be started twice?

No. Once a thread has been started, starting that same Thread object again throws IllegalThreadStateException. Create a new Thread for another run.

24. What is the NEW state?

The thread object has been constructed but start has not yet been called.

25. What is RUNNABLE state?

The thread is executing or eligible to execute. Java's Thread.State does not separate a distinct RUNNING state.

26. What is BLOCKED state?

The thread is waiting to acquire a monitor lock so it can enter a synchronized method or block.

27. What is WAITING state?

The thread waits indefinitely for another thread or action, such as notification or completion after calling join without a timeout.

28. What does join do?

It makes the current thread wait until the target thread terminates, or until a specified timeout if a timed overload is used.

29. Are thread priorities guarantees?

No. Priorities are hints to the scheduler; program correctness must not depend on a particular order or fairness.

30. What does sleep do?

It pauses the current thread for a requested duration, subject to scheduling. It does not release monitors the thread holds.

31. What is a race condition?

A race condition occurs when the program's result depends on uncontrolled timing among operations, commonly concurrent reads and writes to shared mutable state.

32. What does synchronized guarantee?

It provides mutual exclusion on a monitor and memory-visibility ordering around lock and unlock actions. It protects state only when competing code uses the same lock.

33. What lock does a synchronized instance method use?

It locks the receiver object, the object referred to by this for that invocation.

34. What lock does a synchronized static method use?

It locks the Class object representing the declaring class, not an individual instance.

35. What must be true before calling wait?

The current thread must own the monitor of the object on which it calls wait, usually by being inside a synchronized block using that object.

36. Why test a wait condition in a while loop?

A notification does not prove the condition is true, and spurious wakeups are permitted. The thread must recheck the condition after it reacquires the lock.

37. Difference between notify and notifyAll?

notify wakes one arbitrarily chosen waiter on that monitor; notifyAll wakes all waiters, which then compete to reacquire the lock.

38. What is a deadlock?

A deadlock is a cycle where threads wait forever for locks held by one another. Consistent lock ordering can prevent many such cycles.

39. Name the four classic deadlock conditions.

Mutual exclusion, hold-and-wait, no preemption, and circular wait. Breaking at least one condition prevents that deadlock model.

40. What should code do when interrupted?

It should respond cooperatively. If it cannot propagate InterruptedException, it should usually restore the interrupt flag with Thread.currentThread().interrupt() after cleanup.
